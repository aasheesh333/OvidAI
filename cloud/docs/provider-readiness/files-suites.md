## Effects, downloads and exclusions

- All exported candidate operations are reads. Dropbox POST calls are documented read RPCs/content downloads, not mutations. No file/folder create/upload/delete/share, Docs create/batchUpdate, Sheets create/append, Calendar insert/notification, Tasks insert/clear, Gmail draft/send, Outlook draft/sendMail or arbitrary Microsoft Graph operation is exported.
- Calendar event insertion is a persistent `write` and may cause `external_communication`; mail sending is `external_communication`. Neither is downgraded to `mode`, and neither was called in contract or live testing.
- Dropbox binary content download is distinct from Google-native `/export`. Box/OneDrive/SharePoint downloads are not exposed because their redirect/content behavior needs separate reviewed handling. There is no Google `alt=media` escape hatch and no unbounded download, raw MIME, arbitrary range or arbitrary next-page host.
- OAuth access tokens are supplied only through the per-call provider OAuth resolver. `ctx.secrets` is never searched for `access_token`, Firebase ID tokens or Google sign-in tokens. Missing lifecycle resolution fails before egress. Dropbox PKCE exchange sends the exact public `client_id` with `code_verifier` and `redirect_uri`; public profiles never fall back to a supplied client secret.
- Handler arguments are deeply snapshotted/frozen once before validation. That same snapshot is authoritative across OAuth resolution, Dropbox metadata preflight and content download/export, so caller mutation cannot change the Docs ID or make preflight/download paths diverge.
- Cross-user fixtures return distinct tenant-A/B response markers and token canaries. Parsed `redacted_json` projections retain only the owning tenant's marker and redact both token-bearing fields; neither tenant's secret or marker appears in the other's result.
- Live consent is not proven by a synthetic MCP UID. After every exchange/refresh, the harness must bind the exact expected provider identity through Dropbox `users/get_current_account`, Box active `oauth2/tokeninfo`, Microsoft Graph `/me?$select=id` (tenant-specific object ID), or Google OIDC `/v1/userinfo` (`sub`). Failed/mismatched revalidation clears token access before any subsequent read; `OAUTH_TEST_USER` is that opaque provider ID, not an email or arbitrary label. These paths and identity gates are currently source-only and their new tests are **UNEXECUTED**.
- Every current Android profile has `androidRedirectUri: null`. This is an explicit static `not provided` blocker before token exchange; environment-only values cannot make an opt-in possible. An actual approved registered profile must be supplied in a later reviewed source change before Android evidence can pass.
- `catalog.ts` retains only Task 8's evidence-gated `FILES_SUITES_CATALOG_MANIFEST` projection. The previous Task 8 runtime handler imports, special-handler classification, and `defaultFactory` branch were reverted. Handler composition/classification is an exact handoff to the catalog/integration owner before any future supported row; no runtime behavior is added by Task 8.
