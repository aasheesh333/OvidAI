# Ovid Cloud P10 — Hardening, Load & Production Cutover Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove the finished cloud stack survives production: a 100-concurrent-user load profile and a failure-recovery (chaos) suite pass against an isolated staging composition with dated committed evidence; the security corpus (sandbox isolation, auth surface, secrets, dependency audits) becomes permanent tests; monitoring and alerting are live; runbooks and a conditional rollout plan exist; one acceptance command produces the release-evidence file.

**Architecture:** Everything is built from what P1–P9 shipped. A new workspace app `cloud/apps/load` (Node/TS, reusing `@ovid/shared` schemas) is the load generator, the chaos orchestrator, and the metrics/report engine — one language for clients, ground-truth diffing (Redis Streams `readSince` + Postgres mirror), and container/process orchestration. Staging = a second docker-compose project (`ovid-cloud-staging`) on the same box with its own Postgres container, its own redis-q, its own mock-LiteLLM process, scratch loopback ports, and host-run staging worker processes (P2's worker is a host process, not a container). Security tests live in `cloud/apps/e2e/src/security/` so they run in the permanent suite. Monitoring is a new workspace app `cloud/apps/watch` driven by a systemd timer, alerting through mint's existing Telegram mechanism. Rollout and runbooks are owner-gated documents under `cloud/deploy/`, structured like P1 Task 11: artifacts + dry validation autonomous, activation owner-present.

**Tech Stack:** Node 22, pnpm workspaces, TypeScript strict, Vitest, `ws`, ioredis, BullMQ 5, Fastify 5, Docker Compose (staging project), systemd (watch timer, staging worker), nftables/cgroups v2/bubblewrap (exercised, not re-built), `pnpm audit` + `pip-audit`, Telegram Bot API (alerts).

**Spec:** `docs/superpowers/specs/2026-10-15-ovid-cloud-migration-design.md` — G11, §9 (revised here for the actual 8 vCPU/22GB box), §11, §13, §14 P10 row, R6.

**Cross-plan interface contract.** P10 executes last; P2–P9 plans were written in parallel with this one. Where a task below consumes a P2–P9 surface, it pins the *capability* plus a default name/signature and marks it `[MAP]`: the controller reconciles each `[MAP]` against that plan's Produces block (and the ledger's ruling pattern, e.g. progress.md rows for T7↔T9) at dispatch time. Renaming a consumed symbol is a dispatch-edit, never an implementer decision. P1 surfaces (`buildGateway`, `createQueues`, `createRedisEventLog`, `createTicketStore`, `createTestVerifier`, `sweepStaleRuns`, `EventLog.readSince/append/subscribe`) are final and used verbatim.

## Global Constraints

- New code only under `cloud/`; deploy artifacts under `cloud/deploy/`. Never edit `/opt/ovid-gateway/docker-compose.yml` or the live Caddyfile without a timestamped backup + `docker compose config -q` / `caddy validate` first (P1 rule; only Task 13's owner-gated rollout may touch them, via DEPLOY.md §6/§10 procedures).
- **Load and chaos runs NEVER touch production paths.** Staging isolation guarantees, all enforced by `staging.sh guard` (Task 1): separate compose project `ovid-cloud-staging`; separate Postgres *container* + database `ovid_cloud_staging` on `127.0.0.1:15432`; separate redis-q *instance* on `127.0.0.1:16379` (same pinned config: `--maxmemory 1400mb --maxmemory-policy noeviction --appendonly yes --appendfsync everysec`); staging gateway on `127.0.0.1:18082`; mock LiteLLM on `127.0.0.1:14000`; all ports loopback-only; staging worker uses a distinct workspace root (`/workspaces-staging`) and a distinct sandbox uid base (`OVID_SANDBOX_UID_BASE=220000`, prod default `200000`); BullMQ prefix `bull:staging`; **no Caddy involvement until Task 13**.

## Review Focus

1. **Staging bleeds into production** — a staging worker/gateway/test pointed at `ovid_cloud`, the live redis, the live workspace root, or the prod uid base would corrupt or DoS real traffic. Expected: staging tooling refuses to start on any prod-valued env, and every staging session proves the live stack untouched before and after. Pinned by Task 1 guard tests (`staging.sh guard` rejects prod values; `assertLiveUnaffected`), re-run in Tasks 5/6/7/14.
2. **The load harness measures itself** — slow client-side consumption or harness CPU inflates p95 and hides real latency; at 100 users the generator must provably not be the bottleneck. Expected: measured delivery latency against a known in-process baseline stays under a pinned floor, and client event queues drain. Pinned by Task 4 latency-floor self-test + Task 5 harness-headroom row in the report.
3. **A chaos scenario passes vacuously** — the run finished before the kill, the queue was empty before the redis restart, the sweeper fired on an already-failed row. Expected: every scenario gates on a proven precondition (deferred-gated mock LLM holds runs mid-stream; `waiting == N` asserted before restart) before injecting the failure. Pinned by Task 6/7 precondition gates inside each scenario.
4. **The security corpus silently never runs** — CI boxes lack bwrap/cgroups/loop mounts; skip-if guards turn red-suite-green forever. Expected: skips are loud and counted; the release-evidence file fails if the sandbox corpus was skipped on the release box. Pinned by Task 8 skip-reporting test + Task 14 acceptance gate.
5. **The monitor cries wolf or stays silent** — level-triggered checks re-alert every minute (fatigue → ignored), or a dead Telegram token swallows alerts (blind). Expected: edge-triggered state transitions only, plus a `--self-test` that proves the delivery path end-to-end at install. Pinned by Task 11 state-diff tests + self-test gate.

### Task 4: `@ovid/load` — load harness core (client, scenarios, metrics, mock LLM)

**Tool decision (locked): Node/TS generator, not k6.** Rationale: (1) protocol fidelity — every server frame is validated through the *same* zod schemas the gateway emits (`wsServerMsg` from `@ovid/shared`), so client drift is impossible; (2) zero-loss acceptance requires diffing delivered seqs against `EventLog.readSince` ground truth and Postgres rows — native in-process, but custom xk6 extensions in k6; (3) no new toolchain (xk6 custom builds; goja cannot import the TS workspace); (4) 100 users × a few WS frames/s is trivial for one Node event loop — and the harness proves it isn't the bottleneck via the latency-floor self-test (Review Focus #2); (5) the same app hosts the chaos orchestrator (Task 6) and report writer. k6's VU isolation and built-in dashboards buy nothing at this scale.
